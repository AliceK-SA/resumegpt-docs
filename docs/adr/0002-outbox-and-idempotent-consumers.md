# ADR-0002. Transactional Outbox и идемпотентные получатели

- **Статус:** Принято
- **Дата:** 2026-10-13

## Контекст

Сервис часто должен сделать две вещи сразу: изменить свою базу и отправить сообщение. Например, analysis-service переводит заявку в `FAILED` и отправляет `credits.release-requested`. Это две разные системы (PostgreSQL и RabbitMQ), общей транзакции у них нет:

- сначала `COMMIT`, потом публикация, а между ними процесс упал → заявка `FAILED`, а команда возврата не ушла: **кредит пропал**;
- сначала публикация, потом `COMMIT`, а `COMMIT` не прошёл → кредит вернули по анализу, который в базе так и не завершился.

С другой стороны, сообщения иногда доставляются повторно: получатель обработал, но не успел подтвердить. Повторная `credits.release-requested` не должна вернуть кредит дважды.

## Варианты

Для отправки:

1. **Публиковать из кода после `COMMIT`.** ➕ Просто. ➖ Теряем сообщения при падении между двумя действиями. Для денег недопустимо.
2. **Transactional Outbox.** Сообщение пишется в таблицу `outbox` той же транзакцией, что и бизнес-данные; фоновый relay отправляет его в брокер. ➕ Сообщение не теряется. ➖ Возможны дубли (доставка «как минимум один раз»), задержка до 1 с.
3. **Change Data Capture (Debezium).** ➕ Не нужен свой relay. ➖ Kafka Connect + Debezium — тяжёлая инфраструктура для учебного проекта.

Для приёма:

1. **Надеяться, что дублей не будет.** ➖ Будут.
2. **Таблица `inbox`** с id обработанных сообщений. ➕ Просто и универсально.
3. **Только естественная идемпотентность** (условные `UPDATE`, уникальные индексы). ➕ Без лишней таблицы. ➖ Не везде её легко обеспечить.

## Решение

**Outbox у всех сервисов с базой (analysis, billing, payment), `inbox` у всех получателей с базой, плюс условные `UPDATE` и уникальные индексы как второй рубеж.**

Отправка:

```sql
BEGIN;
  UPDATE analyses SET status = 'FAILED', credit_status = 'RETURNED'
   WHERE id = :id AND status = 'PROCESSING';
  -- если обновилась 1 строка:
  INSERT INTO outbox (id, routing_key, payload, publish_after)
       VALUES (:eventId, 'credits.release-requested', :json, now());
COMMIT;
```

Relay раз в секунду:

```sql
SELECT * FROM outbox
 WHERE sent_at IS NULL AND publish_after <= now()
 ORDER BY created_at LIMIT 100
 FOR UPDATE SKIP LOCKED;
-- публикуем в RabbitMQ с publisher confirms
UPDATE outbox SET sent_at = now() WHERE id = ANY(:confirmed);
```

- `FOR UPDATE SKIP LOCKED` позволяет запускать несколько экземпляров сервиса: одну строку не отправят двое.
- Колонка `publish_after` даёт отложенную отправку — так сделаны паузы между попытками анализа, без плагинов RabbitMQ.

Приём:

```sql
BEGIN;
  INSERT INTO inbox (event_id) VALUES (:eventId);   -- PRIMARY KEY; конфликт → уже обработано
  ... бизнес-логика + свои сообщения в outbox ...
COMMIT;
-- затем ack сообщения
```

**Исключение — ai-worker.** У него нет базы, а значит, нет outbox и inbox. Его защищают другие механизмы: от повторной обработки — аренда задачи ([ADR-0004](0004-stateless-worker-with-lease.md)), а результат он публикует с publisher confirms. Если воркер упадёт до публикации, задачу вернёт watchdog. Дубль результата отсеет inbox в analysis-service.

**HTTP.** `POST /analyses` и `POST /purchases` принимают заголовок `Idempotency-Key`. Сервис хранит ключ и ответ 24 часа и на повтор возвращает тот же ответ. Внутренние вызовы идемпотентны по бизнес-ключу: резерв — по `analysisId`, платёж — по `purchaseId`.

## Последствия

- ➕ Ни одно сообщение не теряется: неотправленное лежит в `outbox` и уйдёт, когда поднимется брокер или сам сервис.
- ➕ Повторная доставка безопасна в любой точке.
- ➕ Пока RabbitMQ лежит, сервисы продолжают принимать запросы, сообщения копятся в `outbox`.
- ➖ Задержка доставки до ~1 с — для анализа, который идёт 10–60 с, незаметно.
- ➖ Таблицы `outbox` и `inbox` растут — чистим записи старше 7 дней.
- ➖ Одинаковый инфраструктурный код в трёх сервисах. В части 2 вынесем его в общий Maven-модуль `common-messaging`.
