# ADR-0003. Асинхронный анализ через RabbitMQ с приоритетной очередью

- **Статус:** Принято
- **Дата:** 2026-10-13

## Контекст

В первой версии ResumeGPT анализ выполнялся синхронно: браузер отправлял `POST /analyze` и держал соединение, пока Spring Boot ходил в hh.ru и Groq (10–60 секунд). Проблемы этого подхода:

- длинные HTTP-запросы рвутся по таймаутам прокси и мобильных сетей; пользователь не узнаёт результат, а токены уже потрачены;
- при всплеске нагрузки все запросы одновременно идут в Groq и упираются в его лимиты;
- тариф обещает платным пользователям «без очереди», а при синхронной схеме очереди просто нет — есть только отказы.

Нужен механизм, который принимает задачи, хранит их, раздаёт воркерам с учётом приоритета и переживает перезапуски. Плюс брокер для остальных сообщений: команд по кредитам и событий об оплате.

## Варианты

| | RabbitMQ | Apache Kafka | Очередь в таблице PostgreSQL | Синхронно, как было |
|---|---|---|---|---|
| Приоритет платных задач | ✅ `x-max-priority`, из коробки | ❌ нет приоритетов; только отдельные топики и своя логика выбора | ⚠️ `ORDER BY priority`, но воркерам придётся опрашивать базу | ❌ |
| Надёжная доставка | ✅ durable, publisher confirms, ack | ✅ | ✅ | ❌ |
| Повторы и DLQ | ✅ dead-letter exchange, TTL | ⚠️ строить самим | ⚠️ вручную | ❌ |
| Ограничение нагрузки на Groq | ✅ число воркеров × `prefetch = 1` | ✅ | ✅ | ❌ |
| Хранение и перечитывание истории | ❌ | ✅ сильная сторона | ⚠️ | ❌ |
| Порог входа | Низкий: один контейнер, веб-консоль, Spring AMQP | Выше: партиции, offsets, KRaft | Низкий, но много своего кода | — |

## Решение

**RabbitMQ.** Он уже был в нашем плане развития («RabbitMQ — очередь анализов»).

- Exchange `resumegpt.events` (topic) для всех сообщений.
- Задачи анализа — в очереди `ai.jobs` с `x-max-priority = 10`: продвинутый анализ публикуется с приоритетом 9, базовый — с 1. Пока в очереди есть платные задачи, воркеры берут их первыми.
- У каждого воркера `prefetch = 1`: он берёт следующую задачу, только когда закончил текущую. Нагрузка на Groq ограничена числом воркеров — это наш регулятор расходов и лимитов.
- `analysis.inbox` и `billing.inbox` — с очередями задержки для повторов и DLQ.

Главный довод: нам нужны **очередь задач с приоритетами** и **надёжная доставка с повторами**. RabbitMQ даёт это конфигурацией. Сильные стороны Kafka — огромный поток и перечитывание истории — нам не нужны, а приоритетов в ней нет.

## Последствия

- ➕ Платные анализы обгоняют бесплатные — обещание тарифа выполняется механизмом брокера, а не нашим кодом.
- ➕ Всплеск нагрузки превращается в очередь, а не в ошибки: задачи ждут, пока воркеры освободятся. Добавить воркеров — значит запустить ещё копии контейнера.
- ➕ Веб-консоль RabbitMQ (порт 15672) удобна на защите: видно, как растёт очередь при выключенных воркерах.
- ➖ Бесплатные задачи при постоянном потоке платных могут ждать долго (голодание). В учебной версии принимаем как есть. Если станет проблемой — выделим бесплатным анализам отдельную очередь `ai.jobs.basic` и гарантированный минимум воркеров для неё.
- ➖ Клиенту нужно опрашивать статус. В будущем это можно заменить на Server-Sent Events.
- ➖ Один узел RabbitMQ — единая точка отказа. Смягчение: благодаря outbox ([ADR-0002](0002-outbox-and-idempotent-consumers.md)) недоступность брокера только задерживает сообщения, а не теряет их.
