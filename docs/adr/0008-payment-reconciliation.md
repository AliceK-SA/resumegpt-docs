# ADR-0008. Восстановление платежа при неопределённом ответе провайдера

- **Статус:** Принято
- **Дата:** 2026-11-21
- **Участники:** Климович А., Петроченко П., Хамадалиева Э.

## Контекст

После таймаута запроса создания платежа ЮKassa могла создать платёж, а локальный сервис мог не получить идентификатор и ссылку. Простое возвращение `PENDING` без confirmationUrl навсегда оставит покупку без перехода к оплате.

## Варианты

1. **Всегда создавать новый платёж.** Плюсы: проще. Минусы: риск двух внешних платежей.
2. **Повторять создание с исходным идемпотентным ключом.** Плюсы: можно восстановить идентификатор и ссылку без нового платежа; минусы: требуется состояние восстановления.

## Решение

Для каждого purchaseId создаётся одна локальная запись с постоянным `payment.id` и идентичным `Idempotence-Key` при всех повторах вызова ЮKassa. Если результат неизвестен, платёж остаётся `PENDING_RECONCILIATION` на уровне внутреннего состояния (публично `PENDING`). Повторный `POST /payments` или фоновая сверка восстанавливают creation request с прежним ключом и параметрами; если известен внешний идентификатор, сверяется статус. Повторная отправка не заменяет ключ и не создаёт новый purchaseId.

## Последствия

- Для локальных платежей нужна фиксация тела и ключа исходного запроса.
- Тестируются: таймаут до ответа, повтор после рестарта, неполная запись external ID, дубли вебхуков.
- Финальный ответ 200 допустим только для восстановленного или уже созданного внешнего платежа.
