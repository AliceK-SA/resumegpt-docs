# ADR-0006. Документация как код

- **Статус:** Принято
- **Дата:** 2026-11-19
- **Участники:** Климович А., Петроченко П., Хамадалиева Э.

## Контекст

Архитектура ResumeGPT описана до начала реализации: в части 2 код пишется по контрактам. Значит, документация будет меняться вместе с кодом, и устаревшее описание опаснее, чем его отсутствие. Нужно решить, в каком виде вести документацию, чтобы она:

- менялась в тех же изменениях (pull request), что и код;
- проверялась автоматически — битые ссылки и невалидные контракты должны находиться до слияния;
- была доступна для чтения без установки специальных программ.

## Варианты

**А. Документы в Word по ГОСТ 19, отдельно от кода.**

- ➕ Привычный формат для сдачи.
- ➖ Хранятся отдельно от кода и быстро устаревают; изменения не видны в истории репозитория.
- ➖ Контракты API в Word нельзя проверить автоматически и нельзя сгенерировать по ним код.

**Б. Вики (Confluence и т. п.).**

- ➕ Удобно редактировать.
- ➖ Версия документа не привязана к версии кода, нет ревью изменений.

**В. Документация как код: Markdown, Mermaid, OpenAPI, AsyncAPI в Git, сборка сайта и проверки в CI.**

- ➕ Документ меняется в том же pull request, что и код, и проходит то же ревью.
- ➕ Контракты машиночитаемые: их проверяют валидаторы, по ним генерируется справочник API.
- ➕ Диаграммы — текст: их правки видны в истории, PNG генерируются из кода.
- ➖ Итоговый отчёт для сдачи нужно собирать отдельным скриптом.

## Решение

**Вариант В.**

- Описание архитектуры — по шаблону arc42, диаграммы — в нотации C4 (Mermaid).
- Решения — журнал ADR в режиме append-only ([правила](index.md)).
- Контракты — OpenAPI 3.0 и AsyncAPI 3.0; справочник API генерируется из них скриптом.
- Сайт документации собирается MkDocs Material и публикуется на GitHub Pages.
- При каждом pull request запускаются проверки: линтер Markdown, валидаторы OpenAPI и AsyncAPI, актуальность справочника API, сборка сайта в строгом режиме.

## Последствия

- ➕ Документация не расходится с контрактами: справочник API собирается из тех же файлов, по которым пишется код.
- ➕ Ошибки (битые ссылки, невалидная спецификация) находятся автоматически до слияния.
- ➖ Команде нужно знать Markdown и Mermaid — порог входа низкий.
- ⚠️ Итоговый проектный отчёт — сводка по ГОСТ 19.105: таблицы ADR, API и диаграммы в нём формируются автоматически из репозитория, поясняющий текст пишется вручную. Полные тексты документов ведутся только в `docs/`, отдельный параллельный комплект не ведётся.
