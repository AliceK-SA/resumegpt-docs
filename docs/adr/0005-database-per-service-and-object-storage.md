# ADR-0005. Своя база у каждого сервиса, файлы — в MinIO, в сообщениях — только ссылки

- **Статус:** Принято
- **Дата:** 2026-10-13

## Контекст

В первой версии данные «жили в памяти», базы не было. Теперь нужно хранить:

- заявки и архив результатов — до сотен КБ JSON на анализ;
- файлы резюме — PDF/DOCX до 5 МБ;
- кредиты, покупки, платежи — маленькие, но самые ценные данные.

Нужно решить, как сервисы делят эти данные и где лежат файлы.

## Варианты

Базы:

1. **Одна общая база на всех.** ➕ Можно делать `JOIN`. ➖ Изменение схемы ломает чужие сервисы, сервисы нельзя развёртывать независимо. Тяжёлые запросы к архиву анализов замедляют операции с деньгами. По сути — монолит, разрезанный на процессы.
2. **Отдельная база (или схема) и отдельный пользователь на каждый сервис на одном сервере PostgreSQL.** ➕ Изоляция данных и прав, независимые миграции, простая инфраструктура. ➖ Сервер базы — общая точка отказа.
3. **Отдельный сервер PostgreSQL на сервис.** ➕ Полная изоляция. ➖ Тяжело для ноутбука студента.

Файлы:

1. **В PostgreSQL (`bytea`).** ➖ Раздувает базу и бэкапы, файл приходится гонять через сервис.
2. **Внутри сообщений RabbitMQ.** ➖ Сообщения по 5 МБ — плохая практика: брокер держит их в памяти, растут задержки.
3. **В объектном хранилище S3 (MinIO), в сообщениях — только путь (паттерн Claim Check).** ➕ Брокер и базы остаются лёгкими. ➕ S3 уже был в нашем плане развития. ➖ Ещё один компонент.

## Решение

**Базы — вариант 2 в учебной версии (вариант 3 — целевой для продакшена). Файлы — MinIO с передачей ссылок.**

| Сервис | Хранилище | Кто имеет доступ |
|---|---|---|
| analysis-service | `analysis_db` | только analysis-service |
| billing-service | `billing_db` | только billing-service |
| payment-service | `payment_db` | только payment-service |
| ai-worker | — | — |
| файлы резюме | MinIO, бакет `resumes` | запись — analysis-service, чтение — ai-worker (отдельные ключи доступа) |

Правила:

- Ни один сервис не читает чужую базу. Чужие данные получаем только через API или сообщения.
- В сообщениях `analysis.requested` передаётся путь `resumeObjectKey`, а не файл.
- Результат анализа (JSON, десятки КБ) едет прямо в `analysis.completed` и сохраняется в `analysis_db`.
- Файлы удаляются через 30 дней правилом жизненного цикла бакета (у нас хранится результат, а не исходник). Это же ограничивает объём персональных данных, которые мы храним.

## Последствия

- ➕ Сервисы развёртываются и меняют схему независимо.
- ➕ Отказ или перегрузка `analysis_db` (архив) не мешает операциям с кредитами в `billing_db`.
- ➕ Брокер работает с маленькими сообщениями.
- ➖ Нельзя одним `JOIN` получить «анализы пользователя вместе с его тратами». Экран истории собирается из двух запросов: `GET /analyses` и `GET /credits/history`.
- ➖ Файл в MinIO может остаться «сиротой», если analysis-service упал между загрузкой файла и созданием заявки. Его удалит правило жизненного цикла через 30 дней — допустимо.
- ➖ MinIO — дополнительный контейнер. Если он недоступен, новые анализы не принимаются (`503`), а архив и кредиты работают.
