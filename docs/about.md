# О документации

Документация ResumeGPT ведётся по принципу «документация как код» ([ADR-0006](adr/0006-docs-as-code.md)): она хранится в том же репозитории, что и код, меняется через pull request и проверяется автоматически.

## Структура репозитория

| Путь | Что лежит |
|---|---|
| `docs/index.md` | Главная страница: состав комплекта, соответствие ГОСТ 19.402 |
| `docs/arc42/` | Описание архитектуры по шаблону arc42, разделы 1–12 |
| `docs/adr/` | Журнал архитектурных решений |
| `docs/api/openapi/`, `docs/api/asyncapi/` | Спецификации API — источник истины для справочника |
| `docs/api/*.md` | Справочник API: `index.md` пишется вручную, остальные страницы генерируются |
| `docs/assets/diagrams/` | PNG-копии диаграмм для отчёта и слайдов. В репозиторий не попадают: генерируются из Mermaid при сборке |
| `scripts/` | Генерация справочника API, проверка спецификаций, рендер диаграмм |
| `report/` | Сборка итогового отчёта по ГОСТ 19.105 |
| `mkdocs.yml` | Настройки сайта документации |
| `.github/workflows/docs.yml` | Автоматические проверки и публикация |

## Инструменты

| Задача | Инструмент |
|---|---|
| Тексты | Markdown |
| Диаграммы | Mermaid (нотация C4, диаграммы последовательностей и состояний) |
| Синхронные контракты | OpenAPI 3.0 |
| Асинхронные контракты | AsyncAPI 3.0 |
| Сайт | MkDocs Material |
| Хостинг | GitHub Pages |
| Проверки и публикация | GitHub Actions |

## Правила ведения

1. **Изменение документации — через pull request** в ветку `main`, с ревью хотя бы одного участника команды.
2. **Изменение контракта — сначала в спецификации**, затем в коде. После изменения спецификации запускается `python scripts/gen_api_reference.py`.
3. **Страницы справочника API не правятся вручную**: они перезаписываются генератором.
4. **ADR не переписываются задним числом** ([правила журнала](adr/index.md)).
5. **Диаграммы — только в Mermaid.** PNG не хранятся в репозитории: их генерирует скрипт `scripts/render_diagrams.py` при сборке, поэтому они не могут разойтись с исходником.

## Автоматические проверки

При каждом pull request и каждом изменении ветки `main` GitHub Actions выполняет:

| № | Проверка | Инструмент | Что ловит |
|---|---|---|---|
| 1 | Линтер Markdown | markdownlint-cli2 | Нарушения оформления: заголовки, списки, таблицы, блоки кода |
| 2 | Валидация OpenAPI | openapi-spec-validator | Спецификации, не соответствующие стандарту OpenAPI 3.0 |
| 3 | Валидация AsyncAPI | AsyncAPI CLI | Спецификации, не соответствующие стандарту AsyncAPI 3.0 |
| 4 | Согласованность контрактов | `scripts/check_specs.py` | Битые `$ref`, повторяющиеся `operationId`, каналы без отправителя или получателя |
| 5 | Актуальность справочника API | `scripts/gen_api_reference.py --check` | Справочник не перегенерирован после изменения спецификации |
| 6 | Правила API | `spectral lint` и `scripts/check_contract_rules.py` | Отсутствие 4xx, авторизации и описания пагинации там, где она обязательна |
| 7 | Неприкосновенность ADR | `scripts/check_adr_append_only.py` | Изменения текста принятых ADR относительно базового коммита |
| 8 | Сборка сайта | `mkdocs build --strict` | Битые ссылки между страницами, ошибки навигации |
| 9 | Рендер диаграмм | `scripts/render_diagrams.py` (Mermaid CLI) | Синтаксические ошибки в диаграммах Mermaid |
| 10 | Сборка отчёта | `report/build.sh` | Отчёт не собирается из текущих материалов репозитория |

При сбое проверок workflow завершается ошибкой. **Запрет слияния не обеспечивается одним YAML**: защита `main` должна отдельно требовать успешные status checks `Проверки и сборка` и `Диаграммы и итоговый отчёт`. Настройки GitHub в архиве не представлены, поэтому этот запрет пока не подтверждён. Развёртывание Pages выполняется отдельно; до успешного запуска адрес сайта и скриншот не считаются доказательствами публикации. PDF и DOCX собираются и сохраняются как артефакт, если задача отчёта прошла.

## Как собрать локально

```bash
pip install -r requirements-docs.txt
python scripts/check_specs.py
python scripts/gen_api_reference.py
mkdocs serve            # сайт на http://127.0.0.1:8000
```

Сгенерировать PNG-копии диаграмм (нужен Node.js):

```bash
python scripts/render_diagrams.py
```

Собрать итоговый отчёт (нужны Node.js, LibreOffice и poppler-utils):

```bash
bash report/build.sh    # результат в report/build/
```

## Итоговый отчёт

Итоговый проектный отчёт — сводка документов из этого репозитория, оформленная по ГОСТ 19.105-78. Таблицы с записями ADR, операциями HTTP API и сообщениями, составом сервисов и рисками, а также диаграммы формируются при сборке автоматически из `docs/adr/`, спецификаций и исходников Mermaid. Поясняющий текст отчёта написан вручную в `report/report.js`; полные тексты документов находятся только здесь, в `docs/`.

## Публикация: первоначальная настройка

Выполняется один раз после создания репозитория на GitHub.

1. **Settings → Pages → Source:** выбрать «GitHub Actions».
2. **Settings → Secrets and variables → Actions → Variables:** создать переменную `SITE_URL` с адресом сайта (`https://<логин>.github.io/<репозиторий>/`). Адрес репозитория подставляется в отчёт автоматически.
3. **Settings → Branches → Branch protection rule** для `main`: включить «Require status checks to pass» и отметить задачи «Проверки и сборка» и «Диаграммы и итоговый отчёт».
4. После первого успешного прогона сохранить снимок экрана страницы запуска как `report/ci-run.png` и добавить его отдельным коммитом: при следующей сборке он попадёт в отчёт вместо рамки-заглушки.

Адреса и снимок экрана не вписываются в готовый DOCX вручную: при следующей сборке ручные правки были бы потеряны.

## Контрактные тесты для части 2

После появления Java-сервисов CI должен сравнивать опубликованный `/v3/api-docs` каждого сервиса со спецификациями `docs/api/openapi/*.yaml` (операции, параметры, схемы, коды ошибок). Контрактом считается файл в репозитории; springdoc — диагностическое представление фактической реализации, а не источник требований. Пока реализация не приложена, такой тест не может быть выполнен.
